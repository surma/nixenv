# Google developer documentation style

Use this skill to draft or review clear, consistent, accessible technical documentation.

This skill distills the complete 70-page guide, including its word list and change history.

## Apply the correct authority

Use style authorities in this order:

1. Follow explicit user requirements.
2. Follow the project or product style.
3. Follow this skill.
4. Use the first Merriam-Webster spelling for unresolved spelling questions.
5. Use the Chicago Manual of Style for unresolved nontechnical questions.

Treat these instructions as guidelines, not absolute rules. Depart from them when clarity or reader needs require a different choice.

Apply a departure consistently throughout the document.

Do not apply Google-specific product guidance to unrelated products.

## Drafting workflow

1. Identify the audience, document type, reader goal, and required outcome.
2. Find project terminology and existing conventions before you choose new wording.
3. Put prerequisites and critical constraints before the task.
4. Choose one recommended path for the common case.
5. Draft headings around tasks or concepts.
6. Draft the shortest complete explanation that lets the reader succeed.
7. Add examples, links, code, tables, or images only when they add necessary information.
8. Review the result with the checklist in this skill.

Do not expose this workflow in the document unless the user requests an editorial report.

## Core writing rules

- Address the reader as *you*.
- Use an imperative for instructions.
- Use active voice and present tense.
- Identify the actor when the actor matters.
- Put a condition, location, or goal before its instruction.
- Use simple words and direct sentences.
- Keep most sentences below 26 words.
- Keep the subject and verb near the sentence start.
- Cover one main idea in each paragraph.
- Put the paragraph's critical information first.
- Use one term for each concept.
- Include articles, helper words, and relative pronouns when they prevent ambiguity.
- Use common two-word contractions to create a natural tone.
- Use US English spelling and punctuation.

## Tone

Write like a knowledgeable friend who respects the reader's time.

Keep the tone conversational, friendly, factual, and calm. Do not make the tone frivolous, pushy, formal, or promotional.

Avoid slang, internet abbreviations, idioms, metaphors, jokes, pop-culture references, and culturally specific references.

Do not call a task *easy*, *simple*, *quick*, or *obvious*. These judgments depend on the reader.

Do not use *please* in routine instructions. Use it only for a real request, inconvenience, or apology.

Do not use the first-person plural to address the reader. Do not start an instruction with a contraction of *let us*.

## Safety, accuracy, and longevity

- State only verifiable claims.
- Cite the source for specific performance, cost, or scale claims.
- Avoid superlatives and guarantees.
- Describe security features as risk reduction, not absolute prevention.
- Do not disparage competing products.
- Do not document unreleased features without approved authorization.
- Describe the current product state.
- Avoid time-sensitive words such as *currently*, *new*, *latest*, *now*, and *soon*.
- Distinguish requirements, recommendations, options, and possible outcomes.

Use *must* for a requirement. Use *can* for permission, ability, or an option.

Use *might* for an uncertain outcome. Use *We recommend* only when the authoring organization makes a recommendation.

Avoid *should* because it often hides whether an action is required or optional.

## Accessibility and inclusion

- Make every instruction usable without color, location, sound, or a pointing gesture.
- Use meaningful headings and link text.
- Preserve a logical heading hierarchy.
- Provide useful alt text for informative images.
- Use empty alt text for decorative images.
- Provide text equivalents for information in images, audio, and video.
- Do not introduce information only through an image, symbol, or color.
- Avoid directional references such as *above*, *below*, *left*, and *right*.
- Use the singular *they* for a person of unspecified gender.
- Use precise, literal language instead of ableist, violent, gendered, or exclusionary metaphors.
- Respect the terms that a described community uses for itself.

Preserve exact code, API, UI, and quoted literals. If a literal contains a discouraged term, explain it without adopting that term.

## Structural defaults

- Use sentence case for titles and headings.
- Start task headings with a base-form verb.
- Use noun phrases for conceptual headings.
- Use numbered lists only when order matters.
- Use bulleted lists for unordered items.
- Use description lists for terms paired with explanations.
- Use tables only for data with three or more related fields.
- Use numbered steps for procedures with multiple steps.
- Use one bulleted sentence for a one-step procedure.
- Introduce lists, tables, code samples, and most images with complete sentences.
- Use descriptive links that make sense outside their surrounding sentence.

## Formatting defaults

- Use bold only for named UI elements and run-in headings.
- Use italics sparingly for new terms, words as words, and semantic emphasis.
- Reserve underlining for links.
- Use code font for code elements, commands, filenames, paths, input, and output.
- Use straight quotation marks and apostrophes.
- Use a serial comma.
- Avoid semicolons, slashes, ellipses, and exclamation points.
- Put one space after sentence-ending punctuation.

## Review checklist

Perform these passes in order:

1. **Purpose:** Confirm that the document serves one clear reader goal.
2. **Completeness:** Confirm that prerequisites, constraints, steps, results, and recovery information appear where readers need them.
3. **Accuracy:** Verify commands, code, names, links, claims, and UI labels.
4. **Language:** Check voice, tense, actors, conditions, pronouns, terminology, and sentence length.
5. **Structure:** Check headings, paragraphs, lists, tables, procedures, and information order.
6. **Accessibility:** Check keyboard use, link text, alt text, hierarchy, reading order, and nonvisual equivalents.
7. **Formatting:** Check code font, bold text, punctuation, dates, numbers, units, placeholders, and examples.
8. **Longevity:** Remove unsupported promises, future claims, and unnecessary time references.
9. **Consistency:** Check repeated terms, capitalization, punctuation, and formatting.

When the user requests an editorial report, separate required corrections from optional improvements.
